# 需求开发整理规范

1. 新需求先写入 `plan/<版本>/will`，一个需求一个文件，文件名尽量使用中文。
2. 开发前先确认需求范围；未确认的内容标记为“待确认”，不自行实现。
3. 确认开发后，在同版本的 `doing` 中新增制作计划；一个需求对应一份制作计划。
4. 制作计划至少写清技术方案、开发顺序、接口或数据结构、检查方式和验收步骤。
5. 开发过程中需求有变化时，先更新 `will` 的需求文档和 `doing` 的制作计划，再修改代码。
6. 不增加需求范围之外的功能，不进行无关重构。
7. 功能经用户验收后，再更新对应版本的 `done.md` 和需求索引。

## 提交记录书写规范

1. 提交标题优先使用 `type: 一句话概括` 的形式，`type` 以 `feat`、`fix`、`docs`、`refactor`、`test` 为主。
2. 标题只写一个核心结果，不写过程，不写多个并列动作。
3. 提交正文使用项目符号列出本次变更的关键字段，优先按下面顺序组织：
   - 路由或页面路径
   - 数据表或字段变化
   - 接口新增、调整或删除
   - 测试补充
   - 文档同步
4. 如果这次变更包含数据库迁移、表名变更或字段重命名，正文必须单独说明。
5. 如果这次变更只是文档或规则调整，标题中要明确写出“文档”或“规则”。
6. 提交正文尽量简短，适合直接放进 git 提交记录，不写长篇说明。
