# 网址留存制作计划

## 一、计划依据

本计划对应 [网址留存需求](../will/01-网址留存.md)，只实现第一版已确认的范围：网址增删改查、最多两级分类和 JSON 导出。

## 二、技术方案

- 后端：沿用项目现有 FastAPI 目录约定，接口放在 `backend/app/api`。
- 数据层：使用 SQLAlchemy 建模，SQLite 作为本地数据库。
- 前端：沿用项目现有 `front/src` 结构和统一 API 调用规则，页面不得直接调用 Axios。
- 数据库文件：通过环境变量或配置项指定路径，默认放在本地运行数据目录；运行数据不提交到 Git。
- JSON 导出：由后端从数据库读取完整数据并生成下载响应，前端只负责触发下载。

## 三、数据结构

### 分类表 `categories`

- `id`：主键。
- `name`：分类名称，必填。
- `parent_id`：父分类 ID；一级分类为空，二级分类指向一级分类。
- `created_at`、`updated_at`：时间字段。

业务约束：分类最多两级；不能将二级分类作为其他分类的父分类。

### 网址表 `bookmarks`

- `id`：主键。
- `title`：名称，必填。
- `url`：完整 URL，必填。
- `description`：简介，可为空。
- `category_id`：分类 ID，可为空。
- `created_at`、`updated_at`：时间字段。

数据库结构变更时，必须同步更新 `backend/DATABASE_SCHEMA.md`，遵守数据库结构同步规范。

## 四、后端接口计划

### 网址接口

- `GET /bookmark`：查询全部网址，可按分类 ID 查询。
- `POST /bookmark`：新增网址。
- `GET /bookmark/{id}`：查询单个网址。
- `PUT /bookmark/{id}`：编辑网址。
- `DELETE /bookmark/{id}`：删除网址。

### 分类接口

- `GET /bookmark/category`：查询分类树。
- `POST /bookmark/category`：新增一级或二级分类。
- `PUT /bookmark/category/{id}`：重命名分类。
- `DELETE /bookmark/category/{id}`：删除分类；存在子分类或网址时返回明确错误。

### 导出接口

- `GET /bookmark/export`：导出全部分类和网址。
- 响应为 JSON 文件，顶层包含 `version`、`exportedAt`、`categories` 和 `bookmarks`。

接口文件、API 类和类型文件必须遵守现有的后端路由与前端 API 目录规则。若项目实际路由命名约定不同，开发前先同步修正本计划。

## 五、前端页面计划

1. 创建网址库页面，展示分类树和当前分类下的网址列表。
2. 增加网址表单，支持名称、URL、简介和分类。
3. 增加分类管理入口，支持一级、二级分类的新增、重命名和删除。
4. 在网址列表提供编辑、删除和打开网址操作。
5. 提供 JSON 导出按钮，并展示加载、成功和失败反馈。
6. 不实现登录、标签、搜索、排序、置顶、导入和同步入口。

## 六、开发顺序

1. 确认前后端实际目录、启动方式和 SQLite 配置方式。
2. 创建 SQLAlchemy 模型、数据库初始化和迁移/建表流程。
3. 创建分类接口，完成两级分类校验和关联删除校验。
4. 创建网址接口，完成 URL 校验、增删改查和分类关联。
5. 创建 JSON 导出接口，并验证导出结构稳定。
6. 创建前端网址库页面和表单，接入统一 API 类。
7. 完成前后端联调和验收检查。

## 七、检查方式

- 后端：执行 Python 语法检查、接口模块导入检查和相关接口测试。
- 前端：只检查本次改动文件的语法和类型问题，非用户要求不执行完整构建。
- 数据库：验证重启后数据仍存在、分类层级限制有效、关联删除提示正确。
- 导出：验证空数据和包含一级/二级分类的数据均能生成有效 JSON。
- 页面：验证新增、查看、编辑、删除、分类操作和导出按钮均可用。

## 八、验收完成条件

- 本地启动后可以通过浏览器访问网址库页面。
- 网址和分类完成增删改查，数据写入 SQLite 并可持久化读取。
- 分类最多两级，非法三级分类操作被拒绝。
- 删除存在关联数据的分类时有明确处理结果。
- JSON 导出内容完整且符合约定结构。
- 未引入需求中明确不做的功能。
