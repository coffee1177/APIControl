# 01 网址留存：状态 0（分类设计）

## 一、本阶段目标

先设计分类后端，不立即开发。分类当前只展示两层，但数据库结构和数据整理方式需要兼容未来三层、四层及更多层级。

本阶段确认后，才进入分类表、分类接口和测试的开发。

## 二、分类数据结构

分类表使用 `web-categories`，包含以下字段：

分类后端文件统一放在 `backend/app/api/web/categories`，与 `/web/categories` 路由保持一致。

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `id` | 分类唯一标识 | 数据库主键，自增 |
| `name` | 分类名称 | 必填，同一个父分类下不可重名 |
| `parentId` | 父分类 ID | 根分类为 `null`，子分类指向父分类 `id` |
| `floor` | 所在层级 | 根分类为 `1`，子分类为父分类 `floor + 1` |

### 字段约束

1. `floor` 由后端计算，不接收前端指定值。
2. `parentId = null` 时，`floor` 必须为 `1`。
3. `parentId` 有值时，父分类必须存在，并且当前分类的 `floor` 等于父分类 `floor + 1`。
4. v0.0.1 暂时限制 `floor <= 2`，但数据库字段和整理算法不写死两层。
5. 分类关系不能形成循环，分类不能将自己或自己的后代设为父分类。

## 三、分类请求数据整理

数据库查询返回扁平分类数据后，后端按以下步骤整理：

1. 按 `floor` 动态分组，不固定只创建两组。
2. 得到类似下面的中间结构：

```json
{
  "1": [],
  "2": [],
  "3": []
}
```

3. 为每个分类节点增加 `children` 数组。
4. 从第一层开始，根据下一层节点的 `parentId`，将节点挂到对应父节点的 `children` 中。
5. 最终只返回第一层节点组成的数组，子级通过 `children` 逐层嵌套。

### 返回结构示例

```json
[
  {
    "id": 1,
    "name": "开发",
    "parentId": null,
    "floor": 1,
    "children": [
      {
        "id": 2,
        "name": "API 文档",
        "parentId": 1,
        "floor": 2,
        "children": []
      }
    ]
  }
]
```

整理逻辑必须依据实际存在的最大 `floor` 循环处理，不能写成只处理一级、二级的固定代码。

## 四、分类接口计划

第一阶段计划提供：

- `GET /web/categories`：查询分类树。
- `POST /web/categories`：新增分类；请求只传 `name` 和 `parentId`。
- `PUT /web/categories/{id}`：修改分类名称或父分类，后端重新计算 `floor`。
- `DELETE /web/categories/{id}`：删除分类。

Swagger 文档中将 `web` 作为网站记录模块标题；上述每个接口都必须配置简短的接口摘要和说明。

删除规则暂定：存在子分类时不允许删除，并返回明确错误。网址表接入后，如果分类下存在网址，同样不允许删除。

## 五、开发顺序

1. 确认本计划中的字段名称、根层级起始值和接口路径。
2. 创建分类模型和数据库结构文档。
3. 实现层级计算、循环检查和两层业务限制。
4. 实现按 `floor` 分组并逐层整理分类树。
5. 实现分类增删改查接口。
6. 编写分类接口和多层整理算法测试。

## 六、验收标准

- 分类表只包含 `id`、`name`、`parentId`、`floor` 四个业务字段。
- 根分类和子分类的 `floor` 由后端正确计算。
- 当前不允许创建第三层分类。
- 查询结果是带 `children` 的分类树。
- 整理算法可以处理任意层级数据，不固定只支持两层。
- 同级重名、父分类不存在、循环引用和非法层级均有明确错误。

## 七、已确认设计

- 数据库和接口字段均使用 `parentId`。
- 分类接口路径使用 `/web/categories`。
- 修改分类时允许更换父分类，并由后端重新计算相关层级。
- 存在子分类时禁止删除；网址功能接入后，存在网址时同样禁止删除。
